# Spec: Helsingborg och nordvästra Skåne (NSR)

Status: utkast, 2026-11-03. Första källtypen i fas 2 i `docs/plans/2026-11-03-fler-kommuner.md` (NSR före SRV, beslut 2026-11-03).

## Bakgrund

NSR (Nordvästra Skånes Renhållnings AB) hämtar avfallet i Helsingborg, Ängelholm, Höganäs, Båstad, Bjuv och Åstorp, totalt cirka 274 000 invånare. Tömningskalendern på nsr.se använder en publik JSON-tjänst för sökning och en ICS-fil per adress, utan inloggning, kaka eller nyckel.

Kontrollerat 2026-11-03, med Sopors User-Agent:

```
GET https://nsr.se/api/wastecalendar/search?query=rosenvägen 3
→ {"fp":[{"id":"71d627516ce56271010a40fdb5d01eed","Adress":"Rosenvägen 3","Ort":"Helsingborg",
          "Exec":{"Datum":["2026-11-03", …],"AvfallsTyp":["KÄRL 1", …],"Andrad":[0, …], …}}, …],
   "q":"rosenvägen 3"}

GET https://nsr.se/api/wastecalendar/calendar?query=rosenvägen 3&id=71d627516ce56271010a40fdb5d01eed&calendar_type=ical
→ text/calendar, hela kalenderåret (2026-01-06 … 2026-12-28), SUMMARY "KÄRL 1", "Trädgårdsavfall", "Ändrad: KÄRL 1"
```

- **Sökningen** är fritext på gata och nummer, utan ort: `rosenvägen 3` ger träffar i Helsingborg, Ekeby och Ängelholm. Med komma (`Rosenvägen 3, Helsingborg`) blir det inga träffar. `Exec` har tömningarna ungefär fyra veckor fram, och `Andrad` är 1 för en flyttad tömning.
- **ICS-filen** har hela året, men varje händelse kommer två gånger. Utan `query` svarar den 500.
- **Bokstav efter numret:** NSR gör om `Södra Torggatan 7A` till `Södra Torggatan $1 $2` och hittar ingenting, varken i sökningen eller i ICS-filen. `Södra Torggatan 7` ger 7A bland träffarna.
- **Adresser utan tömningar** (Järnvägsgatan 3, Ängelholm) ger 500 från ICS-filen i stället för en tom kalender.
- **NSR:s id är inte unikt.** `c3edf067…` är både Rosenvägen 34, Helsingborg (tom) och Norra Torggatan 7, Hasslarp. Samma gata och ort kan också ha flera id (Torggatan 7, Höganäs: två abonnemang med olika kärl).
- **Avfallstyper** i ett svep över 355 träffar: `KÄRL 1`, `KÄRL 2` (villornas två fyrfackskärl), `Trädgårdsavfall`, `Restavfall`, `Matavfall`, `Pappersförpackningar`, `Plastförpackningar`, `Metallförpackningar`, `Tidningar`, `Färgat glas`, `Ofärgat glas`, `Blandglas`, `Mat + Rest` och `Tidn./glas/metall` (Höganäs före bytet till fyrfackskärl) samt `Miljöfarligt avfall`.

## Beslut

- **Regel 4.** Tjänsten är den publika tömningskalendern på nsr.se, utan inloggning. Skulle NSR börja kräva inloggning tas källan bort.
- **En ny källtyp, `nsr`**: `{ system: 'nsr' }`.
- **Källan:** `{ id: 'nsr', name: 'NSR', url: 'https://nsr.se', kommuner: [Helsingborg 1283, Ängelholm 1292, Höganäs 1284, Båstad 1278, Bjuv 1260, Åstorp 1277], config: { system: 'nsr' } }`. Id:t får aldrig ändras.
- **Samma skydd som Stockholm och VA Syd** (se `2026-11-02-stockholm.md`, Om källan ändras): okänd form ger ett fel, aldrig en tom lista. Ett id utan träff ger 502, inte 404.
- **Riktiga datum, inga beräknade.** ICS-filen ger hela året, så inget räknas fram. Flyttade tömningar (`Ändrad:`) får en varning.

## Klienten (`src/server/nsr.ts`)

```ts
export const NSR_URL = 'https://nsr.se/api/wastecalendar'
export interface NsrHit { building: EdpBuilding; pickups: { date: string; type: string; changed: boolean }[] }
export async function nsrSearch(q: string, fetchFn?: typeof fetch, timeoutMs?: number): Promise<NsrHit[]>
export async function nsrSchedule(hit: NsrHit, fetchFn?: typeof fetch, timeoutMs?: number, today?: string): Promise<Schedule>
export function parseNsrIcs(text: string): { date: string; type: string; changed: boolean }[]
```

- **Adress-id som EDP:** träffen blir en `EdpBuilding` (`raw` = gatan, `street`, `locality` = `Ort`, `buildingId` = NSR:s id), och adress-id:t blir `edpAddressId`: `rosenvägen-3_helsingborg-71d627516ce56271010a40fdb5d01eed`. Eftersom NSR:s id inte är unikt är det **gata, ort och id tillsammans** som pekar ut adressen, och uppslaget kräver att alla tre stämmer. Formatet får aldrig ändras (regel 3), och ett test låser exemplet.
- **Anropen:** `GET` via `fetchJson` för sökningen och en ny `fetchText` (samma fel och User-Agent, men `text/calendar`) för ICS-filen. 3 s för sökning och 5 s för schema. ICS-filen hämtas med `query=<gatan>` och `id`.
- **Form:** sökningen måste ha en lista `fp`. Varje träff måste ha `id`, `Adress`, `Ort` och `Exec` med listorna `Datum` och `AvfallsTyp` lika långa, och datumen på formen `YYYY-MM-DD`. ICS-filen måste börja med `BEGIN:VCALENDAR`, och varje händelse ha `DTSTART` med ett datum och `SUMMARY`. Allt annat kastar `SourceError('nsr.se svarade med ett okänt format')`.
- **Schemat:** ICS-filens händelser och sökträffens `Exec` slås ihop (samma datum och typ en gång), från i dag och framåt. `Exec` täcker årsskiftet innan NSR har lagt ut nästa års kalender. En `Ändrad:`-händelse eller `Andrad: 1` får varningen "Flyttad tömning enligt NSR." Alla datum är källans egna (`estimated: false`).
- **Bokstaven efter numret** tas bort i allt som skickas till NSR (sökning och ICS-fil). Träffen väljs ändå på hela adressen.
- **Tomt schema:** en adress utan tömningar ger ett tomt schema, som alla live-källor (kalenderfilen svarar 502). Svarar ICS-filen 500 för en träff utan tömningar blir schemat också tomt; för en träff med tömningar är 500 ett fel.

### Fraktioner

`mapWasteType` som för EDP, med tre tillägg i `src/server/fractions-map.ts`:

| Text | Fraktioner |
|---|---|
| `KÄRL 1`, `KÄRL 2` | `karl` med texten "Fyrfackskärl 1" och "Fyrfackskärl 2" (klienten skickar "fyrfack" som beskrivning för `KÄRL <n>`) |
| `Färgat glas`, `Ofärgat glas`, `Blandglas` | `glas` (nytt mönster) |
| `Mat + Rest` | `mat`, `rest` (`+` delar ett kärl som `/`) |
| `Tidn./glas/metall` | `tidningar`, `glas`, `metall` (`tidn` räcker för tidningar) |
| `Miljöfarligt avfall` | `karl` med källans text, ett känt kärl (`isKnownBin`) |
| `Trädgårdsavfall` | `karl` med källans text, ett känt kärl (finns redan) |

## Sökning, uppslag och sajten

- `searchLiveSource` (`src/server/handlers.ts`) får en gren för `nsr`: `nsrSearch(gatan)`, sedan `toAddress` och `matchesPlace` som EDP.
- **Särskiljare:** flera träffar med samma gata och ort får kärlen som särskiljare ("Mat + Rest, Pappersförpackningar …"), och har de samma kärl också nästa tömning ("Matavfall, Restavfall, nästa mån 9 nov."). NSR:s id säger användaren ingenting, så "Byggnad 441d616b…" används inte.
- `lookupAddress` (`src/server/lookup.ts`) får en gren för `nsr`: `queryFromAddressId` → `nsrSearch` med gatan → träffen med samma gata, ort och id → `nsrSchedule`. Ingen träff ger **502**.
- **Kommun per ort:** sex kommuner, så `kommunForLocality` med ortindexet (Ekeby → Bjuvs kommun, Torekov → Båstads kommun).
- **Gatuindex:** `data/osm/<kod>.json` för de sex kommunerna med `npm run build:streets`.

## Bevakningen

- `checkNsrSource` i `scripts/source-checks.ts`, med samma lägen och samma fallback via sajten som de andra.
- Kontrolladressen i `PROBES` är ett adress-id: `nsr: 'rosenvägen-3_helsingborg-71d627516ce56271010a40fdb5d01eed'`. Hittas inte id:t längre blir läget `nytt-format`, eftersom ett nytt id hos NSR skulle bryta alla sparade adresser och kalenderprenumerationer.
- Okända avfallstyper (utom `isKnownBin`) rapporteras som för de andra.

- `nsrSearch` och `nsrSchedule` mot de sparade svaren och för okänd form (`fp` saknas, listor med olika längd, datum i fel format, ICS utan `BEGIN:VCALENDAR`).
- `parseNsrIcs`: dubbletter, `Ändrad:` och radbrytningar enligt RFC 5545.
- Fraktionerna i tabellen.
- Adress-id:t är låst, Ekeby ger `Bjuvs kommun`, och två träffar med samma id men olika gata blandas inte ihop.
